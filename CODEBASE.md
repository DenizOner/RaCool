# RaCool codebase reference

This file describes the current implementation, not execution history or task status. Engineering rules live in [AGENTS.md](AGENTS.md), task tracking lives in GitHub Issues, and automated verification runs via GitHub Actions CI. Update existing sections when interfaces or behavior change; do not append completion reports. Historical document snapshots in docs/archive are non-authoritative.

## Platform and build ownership

RaCool uses an ESP32-C6 revision 0.1, 8 MB flash, ESP-IDF/FreeRTOS, LVGL 9.6.0, a 128x64 SSD1306 OLED, KY-040 encoder, MLX90614 object/ambient sensor, chip temperature sensor, fan relay and two RGB indicators. It is a mains-powered Zigbee router; battery/PMIC/electrical power-cut hardware is not established.

[platformio.ini](platformio.ini) pins espressif32 6.9.0 and the esp32-c6-devkitc-1 board with framework=espidf. PlatformIO owns CMake/Ninja/compiler configuration; CMake Tools does not independently configure on open. The workspace points it to the verified PlatformIO-managed CMake. Generated IntelliSense metadata belongs to PlatformIO. [CMakeLists.txt](CMakeLists.txt), [partitions.csv](partitions.csv), sdkconfig.defaults and dependencies.lock describe build inputs.

Environments: esp32-c6-devkitc-1 (production), esp32-c6-devkitc-1_test (target Unity), native (host), esp32-c6-i2c-trace, esp32-c6-health-report, esp32-c6-startup-sentinel, esp32-c6-boot-frame and esp32-c6-zigbee-report-trace (diagnostics). Diagnostic flags remain off in production. Native USB Serial/JTAG is the primary bidirectional console; ports are selected locally, not hardcoded. UART1 loopback is separate from USB and external wiring.

Product identity is generated from `resources/product-version.json` by `tools/product_version.py`. A clean matching `v` Git tag produces a release identity; other worktrees and explicit source archives produce a SemVer development identity, with `*` marking the short OLED form. The provisional version base is not a declaration of a published release. The read-only `tools/ota/inspect_local_image.py` checks an existing Zigbee OTA container against the current source identity, OTA version, hardware range, slot capacities and ESP app descriptor, and calculates its SHA-512 without producing an OTA index or changing the file. Its successful structural result explicitly remains **signature-unverified and installation-forbidden**; signed-base, cryptographic verification and physical/RF approval are separate gates. The ESP-IDF app descriptor and CLI expose the full identity. Zigbee Basic SWBuildID exposes its SemVer core and prerelease, omitting build metadata to respect its 16-byte limit; generation fails if that still does not fit. The distinct OTA file-version counter retains its existing protocol value. `next` computes a candidate from classified changes; `check-release` verifies the clean tagged worktree, channel, OTA monotonicity, actual firmware descriptor and image hash. `plan-release` requires a strictly ordered release history and one described classification per commit since its last tag; it emits a proposal without creating a tag or publishing an image.

## Source map and composition

Public interfaces under include/ mirror implementations under src/:

| Directory | Responsibilities |
| --- | --- |
| Core | IService, ServiceLocator, SystemInitializer, dependency wiring, EventBus, ErrorHandler, memory support and Localization |
| Management | ApplicationManager, ConfigurationManager, PowerManager, Watchdog, diagnostics, performance/resources, logging and security surfaces |
| Hardware | I2C, infrared/internal temperature sensing, relay, encoder, OLED, built-in and external RGB LEDs, GPIO resources |
| Controllers | ClimateController, UIController, MenuManager, system control and telemetry |
| Communication | Zigbee SDK ownership/endpoints/plugins, DebugConsole and SerialMonitor |
| resources | Translation catalogs, licensed font inputs and metadata |
| tools | Build/resource generators, authoritative converter and portable HA dashboard tooling |
| test | Mirrored module tests/helpers, Infrastructure support, manifests and discovery wrappers |

src/main.c enters SystemInitializer. ServiceLocator and injected interfaces connect services; IService supplies lifecycle only where the module actually implements it. Pure calculations remain independent functions. EventBus invokes captured subscriber callbacks outside its registry mutex and reserves their lifetime until return; busy unsubscription requires retaining resources and retrying.

Zigbee startup has a bounded 20-second admission window for SDK descriptor/reporting persistence. SystemInitializer waits up to 30 seconds for its startup workers. The production splash shares that outer budget and holds progress until actual service readiness; an estimated progress duration does not authorize completion. Network association remains separate from service readiness. During the bounded SDK startup wait, a caller already registered with the SDK task watchdog refreshes only its own watchdog once per second. Unregistered callers are not registered implicitly; feed failure rejects the operation, and the 20-second startup deadline still terminates a stalled SDK wait.

Existing workers own peripheral/control mutations. Producers enqueue copied requests; admission is distinct from completion/readback. Cooperative Stop preserves ownership on timeout, rejects new work while closing and releases resources only after callbacks/operations drain. Console module registration propagates esp_err_t; successful partial entries remain console-owned and registration is not atomic rollback.

## Configuration and reset

ConfigurationManager validates field/block snapshots and persists checked updates through UpdateFields. UpdateFieldsIfUnchanged compares expected field bytes under the same owner lock before validation/persistence; stale edits fail without partial mutation. Field allowlists and shared bounds apply to CLI, OLED, Zigbee and load paths; cross-field failures do not partially apply. GetDefaults constructs an owner default snapshot without mutating live/NVS state; config.diff compares defined fields rather than reserved bytes.

| Block | Layout contract |
| --- | --- |
| Hardware V8 | 76 bytes; version offset 72; built-in startup animation byte 2; preserve prior LED/encoder fields on V7 migration |
| System V4 | 20 bytes; version offset 16; CPU profile byte 13; radio TX profile byte 14; menu auto-exit byte 15. V1–V3 migration enables menu auto-exit while preserving all existing settings. |
| Control V2 | 32 bytes; version offset 28; explicit V1 24-byte/version-offset-20 migration |
| Localization | 8-byte locale code plus 4-byte version; independent of system layout |

Defaults include object calibration 0, CPU Balanced, radio Normal, freeze threshold +4 C and display automatic. Saved user settings are not overwritten merely because defaults change. Factory reset is coordinated through checked defaults/network reset and final restart; reset while the screen is asleep retains darkness until reboot. It is available in OLED/CLI, not exposed as a HA product control.

[DebugConsole CLI reference](src/Communication/DebugConsole/README.md) describes product and Developer Tools routes, mode lifetime, serial helper ownership and tests. Developer Mode is a persisted user preference, default OFF; its CLI changes commit before applying, and the configuration owner migrates old system blobs without interpreting legacy padding. The mode is a usability boundary, not authentication.

## Climate, sensing and fan state

[ClimateController module reference](src/Controllers/ClimateController/README.md) documents wire attributes and control semantics. FanCommands is the shared semantic dispatcher for OLED/CLI/Zigbee. Internal modes are OBJECT_SENSITIVE, ON, OFF and AMBIENT_DELTA; converter IDs are a separate wire contract, not enum-array indexes.

TemperatureSources resolves independent object/ambient choices: 0 is internal, 1..3 are external RAM slots. External values are not persisted, expire after five minutes and fall back to internal sensing; fresh external measurements restore the selected source. Effective temperatures are the values actually selected for control, and delta is effective object minus effective ambient. Delta thresholds are signed -9..+9 C, stored with 0.1 C resolution, default +2/+1 C. Absolute fan thresholds are 20..99 C.

In automatic control, stale IR data cannot produce a new fan decision: retain current fan output and cancel a pending threshold decision until fresh data returns. CPU protection and explicit fan commands preserve priority. Climate's worker owns checked relay writes and timed action deadlines; a GPIO request acknowledgment does not prove physical fan operation.

MLX90614 reads require valid SMBus PEC and sensor error bits. Failed cycles retain readable caches without renewing freshness; valid temperature events require both samples from the current cycle. I2C GetState/CheckHealth use nonblocking atomic resource snapshots, separate from bounded transfer locks and physical bus/device checks. CPU sensing is chip temperature, not room temperature.

CLI includes CLIMATE MODE, SOURCE, DELTA, EXTERNAL, SOURCES, ACTION, SET HIGH|LOW and SAVE. OLED source assignment is omitted; HA/CLI retain it. Fan state is reported on transitions and initial connection independently of periodic temperature reporting.

## Zigbee and Home Assistant

**DIY OTA identity (Product Owner decision, 18 Nov 2026):** No assigned CSA manufacturer code is required for private, amateur RaCool use. EP10's OTA client uses the shared **test-vendor code `0xFFF1`** (not an owned or globally unique manufacturer ID) and the project-local image type `0x1234`, with the existing hardware revision, monotonic OTA file version, model `RaCool-ESP32C6` and displayed manufacturer name `RaCool`. Zigbee2MQTT **local signed-image/index workflow** is the intended #28/#29 delivery channel; no public OTA feed, subscription, vendor claim, automatic update or device HTTP client. Do not change the Zigbee PAN, pairing/NVS, converter or HA identities to implement this. Existing unsigned/legacy clients still advertise old OTA manufacturer `0x1234`, which is used by DSR Corporation, and do **not** migrate merely because the source constant changed. A separately approved, safe signed-base migration and SDK completed-write ACK remain prerequisites to real OTA. Full local matching, verification, no-publication and rollback rules: `tools/ota/README.md`.


**Approved OTA signing policy:** Software-only RSA-v2 signed firmware verification on ESP-IDF 5.3.1, no Secure Boot/eFuse or flash encryption change. The private key is never a repository or CI asset. The current production image is *not* assumed to be a signed trust root; the opt-in, nonproduction `tools/ota/signed-ota.kconfig` and migration boundary are documented in `tools/ota/README.md`. The pure `OtaImageStream` reassembles the fixed Zigbee OTA envelope across consecutive bounded blocks, requires a checked header and writes only the ESP app image into its injected backend. It reports check/apply success only after that backend's actual verification and boot selection; it never restarts a device. It remains disconnected from the SDK callback until worker synchronization is established. The independent `OtaImageWriter` owns ESP-IDF inactive-slot begin/write/verify/boot-selection/abort semantics, but production permits them only with signed-on-update RSA v2 and rollback Kconfig. On pinned ESP-IDF 5.3.1 the writer uses `OTA_WITH_SEQUENTIAL_WRITES` rather than a multi-MiB Begin-time bulk erase; it retains the validated application size locally and limits each write to one 255-byte Zigbee block (at most one incremental 4 KiB erase per call). This reduces per-call flash work but does not prove callback timing/watchdog safety or enable live OTA. An SDK Begin failure can follow partial erase and therefore locks that writer against blind retry. An ESP-IDF Verify `esp_ota_end` NOT_FOUND result (handle absent before SDK cleanup) is also latched as failed instead of clearing a writer for another attempt; ordinary image-verification errors follow ESP-IDF's completed handle cleanup. The stream also treats a failed backend Begin as cleanup-uncertain (there may be no valid handle to abort), so Cancel cannot misreport recovery or admit another transfer. A failed Abort never retries a missing/ambiguous handle. The stream exclusively owns one Abort after a rejected Write/Verify; the writer latches its write error and must not self-abort. The stream attempts backend cleanup only once and locks cleanup-uncertain sessions until owner-directed recovery. Native integration exercises actual stream + writer composition with an ESP-IDF mock. Before flash erase, Begin additionally rejects an OTA target already configured for the next boot, or an unreadable boot choice. Boot selection also compares the SDK's configured boot partition before and after `esp_ota_set_boot_partition`; a failed write or mismatched readback is permanently marked uncertain in that writer lifetime. It must not be retried, aborted as cleaned, or treated as a safe reboot without separate recovery evidence. The unsigned production build has a non-mutating NOT_SUPPORTED backend. It is intentionally not invoked by the Zigbee SDK callback until a bounded asynchronous worker, acknowledged-write delivery, signed-base migration and physical acceptance exist. No callback initiates a reboot. The new pure `OtaImagePolicy` checks OTA manufacturer/type, strictly newer file version, bounds, optional hardware range, header/image tags and contiguous block offsets before any future flash writer, but **is not a cryptographic authenticator**. EP10 still rejects installation until an approved signed base, verified image writer and live tests exist.

EP10 registers the standard Zigbee OTA client cluster. The signed-only image parser/writer and pending-verify rollback gate exist as tested components but are not yet connected to a bounded SDK-safe flash execution/acknowledgement path; the unsigned installed-image trust-root migration also remains unverified. The Zigbee action router initializes OTA progress and Query Next Image results to ABORT **before** attempting its service mutex, so SDK-lock contention, shutdown or missing handlers cannot accidentally retain an old SUCCESS. It rechecks `closing` **after** taking the service mutex: Stop may begin during the wait, in which case it releases the mutex without dispatching any endpoint, leaves OTA as ABORT and returns FAIL for an attribute callback. This closes the pre-acquisition shutdown race; it is not a measured hardware flash-latency guarantee. Until that owner exists, START/RECEIVING/CHECK/APPLY/FINISH OTA progress callbacks explicitly return ZCL ABORT instead of implying firmware was written or installed. An ABORT callback may acknowledge cancellation with SUCCESS; this is not an installation result. This fail-closed policy does not alter fan, system-management or network identity attributes.

The Zigbee service is the sole SDK lifecycle owner. Leases drain before init/deinit; callbacks enqueue bounded copied requests instead of waiting on lifecycle locks. Stop posts one SDK mainloop callback and retains that request across timeouts; the callback invokes SDK stop only after the mainloop is executing. A failed queue admission or callback result leaves the worker owned for an explicit retry, and deinit waits for the mainloop to exit and SDK leases to drain. AF device descriptors are application-owned between `ezb_af_create_device_desc` and a successful `ezb_af_device_desc_register`. With pinned SDK 2.0.5, the registration function clears its SDK-owned root on failed registration; startup/endpoint/reporting-cache/registration failures must therefore free the unregistered tree exactly once before SDK deinit. Once registration succeeds, SDK deinit reclaims the AF device/endpoint tree (ezb_core_deinit/af_desc_deinit); application-side free would double-free it. After mainloop exit and SDK reader drain, the owner calls SDK deinit once and invalidates the application descriptor handle even on partial teardown failure; retries cannot safely assume the core remains intact. Radio boundary wrappers preserve SDK-discarded driver failures without changing driver returns. Mandatory attributes are initialized through SDK factories, never duplicated.

Configuration changes synchronize both LED brightness fields and the shared control attributes. The SDK worker compares fixed-width attribute values and reports changed configuration without waiting for telemetry intervals. Unchanged configuration and source-diagnostic snapshots do not flood reports; failed report submissions retain bounded retry behavior. The existing attribute queue submits at most one report per scheduled 100 ms turn so SDK buffers can drain. The shared ESP timer callback only posts a coalesced byte to a persistent one-slot queue. A dedicated Zigbee reporting worker (priority 4, below visual workers) owns OnConnected, reporting configuration and attribute SDK access; long SDK/storage operations never execute in the high-priority shared timer task. Timer/queue control storage survives Stop/Start, so an already-entered callback cannot notify a deleted task handle. Stop closes SDK admission, drains active leases, stops the timer and cooperatively parks the reporting worker before deleting it; timeout retains its task and SDK owner for checked retry. ZigbeeAttributePolicy shares the active setting routes between descriptor registration and report submission; legacy aliases and command attributes are excluded. Cluster admission marks those readable/writable descriptors reportable through public SDK accessors before registration, and rolls back ownership on failure. Configuration routes bind to the coordinator during converter configuration. Public SDK memory configuration reserves 32 source/destination binding entries for configuration and telemetry routes without erasing network storage. CLI brightness uses raw 0–255 values; OLED and HA present integer percentages (built-in maximum 255, external ZCL maximum 254). OLED rotation changes one percentage point using LEDBrightnessScale; entering or saving without rotation preserves the precise raw selection. Both LED brightness defaults are 255 for fresh configuration and factory reset; saved selections remain unchanged. External hardware brightness 255 maps to ZCL CurrentLevel 254, whose percentage is 100; CurrentLevel 255 is reserved. Both `rgb brightness` and `rgbled_brightness` persist through ConfigurationManager; low-level IRGBLED.SetBrightness remains a temporary worker operation. OLED brightness edits use a three-second temporary worker preview on each LED while the configuration owner remains unchanged; fault and disabled states retain priority.

Six configurable telemetry intervals are fan/object temperature, ambient, CPU, health, memory and uptime. Zero disables unsolicited reports without stopping local sensing/safety. ConfigurationManager owns persistence; startup rebuilds only the public derived reporting dataset before endpoint registration. Connected endpoint notifications are coalesced and retried under contention; disconnect cancels pending notification. Identical queued numeric samples retain the existing revision, retry budget and backoff, including when a producer runs during SDK application: local attribute success does not cancel an outstanding report obligation. Changed samples replace the latest non-relay value while preserving rejected-report debt and backoff, including when the older SDK request fails after replacement; relay edges remain distinct.

SDK report admission can fail while its fixed message pools drain; this differs from an invalid local attribute write. Once a queued write owns a pending report, retry-budget exhaustion cannot discard that delivery obligation. The existing worker releases SDK ownership after a bounded attempt and retries with elapsed 100/200/400 ms capped backoff; the per-entry counter saturates. FIFO preserves relay edge order, disconnect pauses work and cooperative Stop cancels queue ownership only after operations drain. Permanent unsupported/invalid report errors remain explicit failures and release the queue head; local setter failures without a pending report retain their finite attempt budget. SDK admission is not RF delivery proof. The opt-in SDK error trace and legacy-context negative control are described in [the Zigbee diagnostic procedure](test/Communication/Zigbee/diagnostic/README.md); both remain OFF in production.

ZB REPORT <fan|ambient|cpu|health|memory|uptime> [seconds] accesses these intervals. ZB RESTART cycles the SDK owner without erasing credentials; rejoin is asynchronous. ZB TX Eco|Normal|Boost selects configured 0/10/20 dBm, independent of CPU profiles and router receive operation. SDK configured-power readback is not measured RF power/range. ZB ROUTERS provides bounded public neighbor/route/source-route snapshots (64/64/32); these relationships are not observed transit traffic counters.

[tools/racool.mjs](tools/racool.mjs) is the authoritative external converter. Endpoint/property keys are English, product labels Turkish. Renames require discovery/entity/automation/dashboard migration. Display choices are automatic and always-on, with no selectable off mode; temperature display units are not exposed in HA because Zigbee measurements remain Celsius.

Portable HA tooling under tools/home-assistant supports explicit multi-device identity, dynamic mode-dependent controls, paired absolute/delta range sliders and freely selected zone colors. XY is a color encoding, not a separate temperature zone. Hide inactive controls while retaining mode selection. Back up the live dashboard before changes. mdi discovery icons do not guarantee Zigbee2MQTT frontend icon support.

## OLED, encoder and localization

Rainbow Flow uses one shared full-cycle duration, `RAINBOW_CYCLE_DURATION_MS` in `src/Hardware/LEDAnimations/RainbowFlowAnim.c` (6000 ms). Elapsed milliseconds map onto six 256-step color sectors; changing speed does not change the palette, frame interval, independent player state or shared boot epoch. There is no separate external-LED Rainbow period setting.

The OLED root has four branches: Fan, Lighting, Preferences and System. Lighting separates built-in and external indicators, with nested animation and thermal-zone pages. Preferences contains display, language, unit and calibration; System contains status, Zigbee/reporting, energy, advanced telemetry and maintenance. Category focus is remembered; bounded ancestor history supports deep navigation and Back. Built-in enable and display mode reuse existing owner fields without a schema change.

MenuNavigator's shared context policy filters visible states and navigation; MenuManager refreshes configuration/network context before the menu lock and retains prior context on snapshot failure. Hidden editors cancel safely. Object-sensitive mode shows absolute thresholds; ambient-delta mode shows difference controls; fixed on/off hides automatic controls. External source assignment is absent from OLED. OLED region colors use five named preset selectors, not an XY coordinate category. Each zone list uses contextual Limit/Range and Color rows; editor titles retain the zone name. Calibration lists use Radiator/Ambient while their editors retain full calibration titles. Encoder rotation changes a menu-local draft and requests a three-second external LED preview; Save commits the XY pair through ConfigurationManager. Non-preset XY appears as a selectable Custom color slot; cycling preserves its original coordinates until a preset is saved. Exact preset matches omit that slot. A successful Save restarts the three-second preview. Preview is a worker-owned output overlay with elapsed deadlines; normal animation phase advances independently and global-disabled/high-priority output takes precedence. HA retains freely selected colors.

Menu inactivity uses the configured OLED timeout in both display modes. Automatic mode retains screen sleep; always-on mode queues a return to the monitor without powering off when system.menu_auto_exit_enabled is enabled (factory default 1). The CLI command menu auto-exit on/off/status persists and reads this setting through ConfigurationManager; --machine returns enabled=0/1 only after checked persistence/readback. Disabling it keeps an always-on menu open; automatic screen sleep still closes the menu and resumes at the monitor. The OLED Preferences → Display menu edits the same setting through the staged configuration owner; no HA setting is exposed. Accepted navigation is not duplicated; rejected queue admission is retried. Active pairing retains its inactivity exemption. MenuEditSession stages OLED changes through a menu-local IConfigurationManager facade. Navigation, inactivity and shutdown discard unsaved changes; selection presses commit checked field batches. Only edited fields overlay fresh owner snapshots, preserving unrelated HA updates. A guarded static commit snapshot owns payload bytes until the synchronous owner call returns; cancellation prevents reuse until that call drains. Draft batches validate metadata before copying fields, avoiding full-session stack copies. The default menu worker stack is MENU_TASK_STACK_DEFAULT_BYTES (6144 bytes), including synchronous validation/NVS/event callback headroom. Fan mode selection leads into its automatic threshold range and commits mode plus thresholds together; fixed modes commit directly. Persistence failures and stale owner conflicts retain the editor and show an error.

Sleeping OLED wakes only on a button press, returns to the temperature home page before illumination and ignores rotation. CLI/HA changes update settings without waking it. An awake five-second hold accesses pairing; an asleep ten-second hold directly requests factory reset. Short awake press opens the main menu. All three home icon slots center their symbols; the middle identifies all four fan modes, the last reflects fan output, and the link icon varies with coordinator RSSI sampled every 1000 ms. RSSI level changes use 3 dB downgrade hysteresis to avoid flicker at boundaries. The idle status reads “Sistem kararlı”/“System stable”; its fixed-width label uses circular scrolling when localized text exceeds its area. During boot only, both Rainbow players derive phase from the same monotonic epoch quantized to their shared 20 ms frame interval; outside boot their animation clocks are independent. Built-in initialization adopts the active startup timeline before its first frame, without waiting for the UI polling command. BootAnimation releases both LED workers directly at completion/skip; built-in startup release no longer waits for the UI polling cycle. Rejected queue admissions are logged; existing UI/worker reconciliation remains the fallback. Low/medium-priority SystemController INITIALIZING/READY/SETUP indications cannot preempt startup ownership; low-priority selections update the eventual runtime default without resetting startup. High-priority fault/pairing indications retain precedence. Informational Zigbee connection confirmation is deferred until startup ownership ends; duplicate connected/pairing-stop events do not extend the three-second notice. Disconnect, disabled mode and explicit higher-priority output cancel a pending notice. Rainbow renders at full channel resolution; built-in output and external PWM share LEDColorTransfer before master brightness scaling. Shared raw catalog plugins remain uncorrected so external previews do not receive the curve twice. Bounded startup output tracing is opt-in through RACOOL_LED_PHASE_DIAGNOSTIC and disabled in production; its procedure is in test/Hardware/BuiltinLED/diagnostic/README.md.

The root menu is headerless. Category lists use a 24-pixel rail and four 16-pixel icon slots. List rows are 16 pixels; only selected long text scrolls horizontally. Editor headers occupy 18 pixels. Setting pages have no Save footer/separator; confirmation and read-only navigation retain their necessary prompts. Range persistence failures temporarily replace the track with a borderless error at y46. Choice/animation pages use a centered 96x16 value at y24 with side arrows; only long animation names scroll. Numeric pages use value y18 and a 96x4 track at y41, with borderless inline units. OLED cold/warm/hot regions and the active fan strategy use one dual-thumb range editor per pair. The independent built-in boot selection defaults to Rainbow Flow (6), preserving saved selections and the runtime idle animation. Range endpoint numbers use 14 px SemiBold white text without a selection background; solid/outlined thumbs identify the active endpoint; numeric labels and the 14 px degree unit start at y23 (the central unit has a 24x22 box); the range track is at y48. MenuRangeEditor owns shared drafts in the menu layer; object-sensitive fan thresholds pair turn-off/turn-on temperatures (20..99 C), ambient-sensitive thresholds pair turn-off/turn-on differences (-9..9 C): immutable draft frame snapshots, 0.1 C rotation, two-click Lower/Upper flow (Turn-off/Turn-on for fan settings): the first press selects the upper endpoint, the second performs checked persistence and closes editing back to the setting list and checked two-field persistence. Retired upper-bound menu IDs remain hidden for compatibility. Failed writes retain the draft and editor; external owner changes reject stale drafts. Freeze/danger remain independent single thresholds. Display conversions preserve Celsius persistence; Fahrenheit differences use only a 1.8 scale, without the absolute-temperature offset. Confirmation defaults to No; read-only health shows Back and reports Unknown for unavailable data. Pairing uses four fixed 16-pixel bands and reflects network join, not HA application health. The logo is left and version right; production logo duration is 1800 ms; the progress screen waits for actual initialization readiness, bounded by the shared 30000 ms initializer timeout.

SystemInitializer publishes atomic started/active/completed service history without allocating. The boot label uses a UI-owned, fixed-capacity queue of five groups (core system, LEDs/fan, sensors, Zigbee, controllers). History preserves groups completed during the logo. Each distinct visible message remains for at least UI_STARTUP_MESSAGE_MIN_MS (1000 ms); successful groups use localized ready text, active groups preparing text. Failure bypasses the dwell. Normal transition requires real initializer completion and a drained queue, including a one-second Ready message below the progress bar. The final Ready status is not repeated in the upper label; that area is cleared once the stage queue is exhausted. The service deadline is unchanged; late readiness permits only a bounded extra UI dwell budget. Explicit user skip and startup timeout remain escape paths. OLED diagnostic commands register after early UI startup so loading frames can be inspected before radio initialization completes.

IOLED.CopyFrame exposes only the last complete successful SSD1306 page transfer, with sequence/checksum/power/orientation metadata. [capture_frame.py](test/Hardware/OLED/diagnostic/capture_frame.py) preserves raw bytes and renders visible versus stored-RAM previews. [capture_oled_gallery.py](test/Controllers/UIController/diagnostic/capture_oled_gallery.py) traverses reachable pages without changing values or confirming destructive actions. Captured SDK pixels are not optical evidence. `oled_info` reads the display render mode and LVGL pool free/largest-block/usage under the OLED drawing lock, then prints the snapshot after releasing it.

[resources/translations](resources/translations/README.md) contains en.json/tr.json and automatically discovered additional catalogs. LANGUAGE selects the shared CLI/OLED language without restart or wake. Immutable catalog snapshots keep each response/frame consistent. Localization_Apply does not persist by itself; checked ConfigurationManager application precedes it. Translation generation validates keys, NFC and printf consumers. Temperature unit selection is retained in CLI/OLED and affects presentation, not Zigbee measurement units.

[resources/fonts](resources/fonts/README.md) describes licensed Noto Sans SemiBold 2.015 and pinned lv_font_conv generation: 10/14/20 px, 1 bpp, broad Latin/Greek/Cyrillic coverage; icon fonts remain separate. tools/product_resources.cmake runs generators only in real configure, with build-local outputs. tools/platformio_manifest.py fingerprints catalog/font/generator and LOC_PRINTF inputs to invalidate the affected configure cache. Glyph coverage does not imply shaping or physical readability.

## LEDs and power

Built-in and external LED workers share the animation catalog but own independent selection/playback/startup state. Built-in startup is EP2/genOnOff 0x8005 UINT8 and CLI builtin_led_boot [id]. Dark frames do not terminate playback. Global-disabled mode and fault/pairing precedence remain active; configuration refresh preserves phase and timed notification fallback. Explicit external mode selection clears manual override; unrelated/brightness refresh preserves manual color and playback phase.

The common engine is elapsed-time based, nonblocking and wrap-safe. Color/brightness transitions begin promptly and interpolate from current output toward the latest target; animation cadence remains independent. IRGBLED.PreviewColor copies a bounded temporary color request into the existing queue (default 3000 ms, maximum 10000 ms). rgb status --machine exposes preview, preview_r/g/b and preview_remaining_ms; these are worker readbacks, not optical measurements. RGBZoneSelection publishes menu drafts using bounded 32-bit atomic snapshots, retaining exact custom XY while cycling. OLED animation selection and Save use LED_ANIMATION_PREVIEW_MS (5000 ms) from Hardware/LEDAnimations/LEDPreviewConfig.h; color selection and Save retain RGBLED_COLOR_PREVIEW_MS (3000 ms). Both LED interfaces expose bounded PreviewAnimation requests; each existing worker owns a separate catalog instance and continues normal playback behind its temporary output overlay. OLED animation rotation previews a staged selection without persistence; a successful selection press saves it and restarts its preview. Built-in notification priorities and disabled mode override preview. Worker status is a logical target; LEDC duty and physical color are separate evidence.

PowerManager applies checked esp_pm_configure CPU profiles independently of radio TX. Router operation retains automatic light_sleep_enable=false; explicit deep sleep disables the radio. Wake/reset cause, OLED wake and actual electrical power are distinct. Recovery and watchdog workers use bounded ownership/stop acknowledgment; the shared esp_timer dispatcher is not registered as a watched task.

The production bootloader enables ESP-IDF application rollback. A newly installed image remains `PENDING_VERIFY` until the normal startup path completes and the OTA recovery gate confirms two consecutive checks of persistent ConfigurationManager snapshot and critical service readiness (relay, infrared worker, ClimateController, Zigbee SDK mainloop-owner liveness (not a stale STARTED state) and watchdog health). Zigbee RF association and a single MLX sample are not first-boot prerequisites. Failure requests rollback only when ESP-IDF reports a bootable fallback; unknown boot state or missing fallback is not treated as success. This gate runs only for pending OTA images, never changes NVS/network identity or a relay output, and requires a real device boot/rollback test before physical acceptance.

Native tests inject boundaries; target wrappers reach real SDK/FreeRTOS cases and restore production in finally. Named case inventory and complete warning-free captured build/upload output are required. Live helpers must save fresh baselines, correlate protocol evidence and verify restoration; software evidence never substitutes for physical OLED/LED/encoder/cable acceptance.

The Zigbee live helper rejects pending bridge RPCs when MQTT transport closes and records the result only after cleanup settles. For a selected reporting interval without traffic/other mutations it validates the control/property pair, device identity and correlated raw ZCL read; foreign or uncertain delivery forbids automatic restoration. Global Zigbee2MQTT log mutations are unrelated to RaCool's ESP-IDF LogManager (which is CLI-only and runtime-only). Mutation-capable test-helper modes are disabled before configuration read or socket creation unless the separate explicit `RACOOL_ALLOW_BRIDGE_LOG_MUTATION=1` diagnostic opt-in is provided; this opt-in does not bypass the live non-retained evidence and restoration conditions. Baseline ZCL reporting-interval recovery without traffic requires no global bridge log writes. Temporary global bridge log changes are journaled as requested → acknowledged → live-verified, with baseline raw values validated against the running bridge/info config_schema (current Zigbee2MQTT uses `warning`, older `warn` only when explicitly advertised). ACK alone or retained bridge/info is not confirmation. A non-retained bridge/info update after the request and a new-connection snapshot/readback are both required before reporting restored. Normal finally-path log restoration also checks the latest non-retained bridge/info value and version against the last helper-confirmed level before **every** new global write; known foreign changes or stale-only observations prohibit writes. Recovery final readback must itself be non-retained to claim `restored`; retained-only final readback returns `final_snapshot_unverified` without retrying the write. An older retained broker snapshot alone remains unverified; uncertain delivery, schema/version drift or foreign changes forbid automatic writes or PASS. Bridge read-compare-write is still non-atomic and can race other administrators; no absolute persistence guarantee is claimed. Only correlated, helper-owned bridge RPC responses are summarized as safe command/status metadata, never full payloads; unrelated wildcard responses including Base64 backups are not logged or serialized. Even a matched RPC error is untrusted and mapped to a fixed redacted message; its broker-supplied error text or backup data is never carried into console/JSON. Global log changes now require a fresh non-retained bridge/info **baseline before the first write** and again in each recovery read/write child connection; a retained-only recovery read returns `snapshot_only` without a write, and the set child independently rejects a retained-only baseline, and controlled disconnect flags fail closed on incompatible modes, multiple controls, a debug starting level or a requested disconnect that never occurred. Recovery child processes never inherit the parent's test-only cut flags. Full bridge/config payloads are not written to diagnostic JSON. A test-only opt-in `RACOOL_TEST_CUT_CLIENT_AFTER_WIRE=1` interrupts **only the helper MQTT connection** after a single reporting-interval mutation is confirmed by a new correlated ZCL read (normal `verify` with traffic, change and reconfigure options disabled); recovery children use separate connections and enforce the existing exact-device/conditional raw readback contract. This permits a controlled single-client disconnect acceptance without restarting or proxying the production broker; the option is disabled by default. A separate opt-in `RACOOL_TEST_CUT_CLIENT_AFTER_BRIDGE_LOG=1` in single-control `verify` with traffic observation interrupts only the same test client's TCP socket after ACK **and** a matching live non-retained bridge/info update for its helper-owned global log change; existing separate-connection conditional restoration must still be verified and foreign/unknown writes never retried. Neither fixture proves real bridge/network acceptance. Other control mutations have no automatic recovery.
